Read all 9 Bipedal Ambi config files listed in context. For each requirement below, document the finding with exact file paths, line numbers, and values.

**AUDIT-01: Serial Driver Type**
- Confirm `SERIAL_DRIVER = vendor` in `rules.mk` (line 5)
- Trace: `vendor` -> `builddefs/common_features.mk` line 699 -> compiles `serial_vendor.c`
- Confirm `serial_vendor.c` is PIO-based (uses `pio_claim_unused_sm`, NOT ChibiOS SIO/UART HAL)
- Verdict: CORRECT for RP2040. The vendor driver uses PIO state machines directly via the RP2040 SDK.

**AUDIT-02: TX/RX Pin Assignments**
- Left: `SERIAL_USART_TX_PIN GP0`, `SERIAL_USART_RX_PIN GP1` (keymaps/vial_left/config.h)
- Right: `SERIAL_USART_TX_PIN GP17`, `SERIAL_USART_RX_PIN GP16` (keymaps/vial_right/config.h)
- Document: For full-duplex to work, left TX (GP0) must be wired to right RX (GP16) via TRRS, and left RX (GP1) must be wired to right TX (GP17) via TRRS
- Flag: Cannot verify PCB routing from firmware alone -- user must confirm TRRS jack wiring from schematic/PCB files
- Check for pin conflicts: GP0/GP1 not used elsewhere in left config; GP16/GP17 not used elsewhere in right config (the right matrix uses different pins)

**AUDIT-03: PIO Peripheral Assignments**
- Serial: `SERIAL_PIO_USE_PIO1` defined in `config.h` -> serial uses PIO1
- WS2812: No `WS2812_PIO_USE_PIO1` defined -> WS2812 defaults to PIO0
- Left half: `WS2812_DI_PIN` is `#undef`'d in left config.h -> WS2812 driver is effectively disabled -> PIO0 is FREE, PIO1 used by serial only -> NO CONFLICT
- Right half: `WS2812_DI_PIN GP24` is NOT undefed (only left does this) -> WS2812 driver may initialize on PIO0 with GP24 -> BUT GP24 is not a valid right-side pin (right matrix uses GP1-GP5, GP10, GP11, GP25-GP27) AND `WS2812_DI_PIN GP24` comes from board-level config.h which is SHARED
- CRITICAL CHECK: Does the right half actually try to initialize WS2812? Read `rules.mk` -- `WS2812_DRIVER = vendor` is in the board-level rules.mk, and the right keymap rules.mk does NOT disable it. If WS2812 initializes on the right half, it will try to use PIO0 and GP24.
- Contrast with bipedal65: Uses `WS2812_PIO_USE_PIO1` to move WS2812 to PIO1 (no serial on that board). The bipedalambi approach moves serial to PIO1 instead.
- Verdict: Serial on PIO1, WS2812 on PIO0 -- SEPARATE. But right half may wastefully initialize WS2812 on PIO0 (benign if GP24 isn't connected to LEDs on the right PCB).

**AUDIT-04: Full-Duplex Configuration**
- `SERIAL_USART_FULL_DUPLEX` defined in board-level `config.h` (line 6)
- In `serial_vendor.c`, full-duplex means: separate TX and RX state machines, separate pins, TX uses `out pins` (not `out pindirs`)
- `SERIAL_USART_PIN_SWAP` is NOT defined anywhere
- Without PIN_SWAP: master calls `pio_init(tx_pin, rx_pin)` and slave also calls `pio_init(tx_pin, rx_pin)` (see lines 433-462)
- This means: BOTH halves transmit on their own TX pin and receive on their own RX pin
- For this to work: Left TX (GP0) -> wire -> Right RX (GP16), Left RX (GP1) -> wire -> Right TX (GP17)
- This is the standard TRRS full-duplex crossing -- the PCB/cable must cross TX/RX between halves

**AUDIT-05: Split Detection Config**
- `SPLIT_USB_DETECT` defined in board-level `config.h` (line 7) -- master/slave determined by USB connection
- No `EE_HANDS`, `MASTER_LEFT`, or `MASTER_RIGHT` defined
- `SPLIT_USB_DETECT` requires both halves to be powered and communicating for the slave to detect it is NOT the USB-connected side
- Risk: If serial communication fails at boot, the slave may not properly identify itself, creating a chicken-and-egg problem
- Note: This is a lower-priority hypothesis -- SPLIT_USB_DETECT is standard and works on many boards

**AUDIT-06: ChibiOS Peripheral Activation**
- `halconf.h`: `HAL_USE_SIO TRUE` -- enables ChibiOS SIO (hardware UART) HAL driver
- `mcuconf.h`: `RP_SIO_USE_UART0 TRUE`, `RP_SIO_USE_UART1 TRUE` -- activates both hardware UARTs
- CRITICAL FINDING: The vendor serial driver (`serial_vendor.c`) does NOT use ChibiOS SIO/UART at all. It directly programs the RP2040 PIO peripheral via the Pico SDK (`hardware/pio.h`). The `serial_usart.h` header conditionally defines `QMKSerialDriver` as `SIODriver` when `HAL_USE_SIO` is true, BUT this code path is only used by `serial_usart.c` (the `usart` driver), NOT by `serial_vendor.c`.
- The `HAL_USE_SIO TRUE` tells ChibiOS to initialize its SIO driver infrastructure. `RP_SIO_USE_UART0/UART1 TRUE` tells ChibiOS to configure UART0 (pins: default GP0/GP1) and UART1 (pins: default GP16/GP17) hardware peripherals.
- POTENTIAL CONFLICT: ChibiOS SIO driver initialization may configure GPIO mux for GP0/GP1 (UART0) and GP16/GP17 (UART1) as hardware UART pins. The PIO vendor driver then tries to set these same pins to PIO mode (`PAL_MODE_ALTERNATE_PIO1`). Depending on initialization order, the ChibiOS SIO init could interfere with or override the PIO pin configuration.
- Cross-reference: bipedal65 (non-split, no serial) does NOT define `HAL_USE_SIO` or enable any UARTs -- only `HAL_USE_I2C`. This suggests the SIO/UART config was added specifically for the Ambi's serial communication, but was written for the WRONG driver type (USART instead of PIO vendor).
- `HAL_USE_ADC TRUE` and `RP_ADC_USE_ADC1 TRUE` -- needed for joystick, unrelated to serial. Fine.
- `HAL_USE_I2C TRUE`, `RP_I2C_USE_I2C0/I2C1 TRUE` -- needed for OLED on both halves. Fine.

**AUDIT-07: info.json Split Config**
- `info.json` has `"split": { "enabled": true }` -- minimal, no serial pin config
- No `"serial"` key in info.json -- all serial config is in config.h files
- No conflict between info.json and config.h/rules.mk split settings
- `matrix_pins` in info.json matches the LEFT half pin assignments (this is expected -- QMK uses board-level as default, keymaps override)

In the same SERIAL-AUDIT.md file (appended after the per-requirement sections), create a "Hypothesis Priority List" section that ranks suspected serial failure causes from most to least likely. Each hypothesis must reference specific audit evidence.

The ranking should be based on these criteria:
- Severity: Could this PREVENT serial communication entirely?
- Confidence: How certain are we from config analysis alone?
- Testability: Can this be tested with a single firmware change?

**Expected hypotheses (rank based on audit findings):**

H1: **HAL_USE_SIO / UART peripheral conflict** (from AUDIT-06)
- ChibiOS initializes hardware UART0/UART1 on the same pins the PIO driver needs
- SIO driver may set GPIO mux to UART function before PIO driver sets it to PIO function
- Fix: Remove `HAL_USE_SIO TRUE` from halconf.h and `RP_SIO_USE_UARTx` from mcuconf.h
- Confidence: HIGH -- this is a clear config mismatch (vendor driver = PIO, not SIO/UART)
- Maps to: New test (not currently in DIAG list -- recommend inserting as DIAG-00 or modifying DIAG-01)

H2: **PIO conflict on right half** (from AUDIT-03)
- WS2812 driver may initialize on PIO0 for the right half (WS2812_DI_PIN not undefed)
- Serial uses PIO1 (SERIAL_PIO_USE_PIO1), so the PIOs are separate
- But WS2812 trying to use GP24 on the right half (where GP24 is not an LED pin) could cause unexpected PIO0 state machine allocation issues
- Fix: Explicitly `#undef WS2812_DI_PIN` in right keymap config.h (like left does) or add `WS2812_DRIVER = none` to right rules.mk
- Confidence: MEDIUM -- PIOs are separate, but unnecessary driver init is a risk
- Maps to: DIAG-01 (modified scope)

H3: **TX/RX wiring mismatch** (from AUDIT-02, AUDIT-04)
- Cannot verify PCB routing from firmware -- if TX/RX are not crossed on the PCB or TRRS cable, full-duplex fails silently
- The TRRS jack may connect left GP0 to right GP17 (TX-to-TX) instead of left GP0 to right GP16 (TX-to-RX)
- Fix: Try `SERIAL_USART_PIN_SWAP` or swap TX/RX pin definitions
- Confidence: MEDIUM -- power works (OLED lights up on slave) which confirms VCC/GND routing, but data lines are unverified
- Maps to: DIAG-03, DIAG-04

H4: **Half-duplex as workaround** (from AUDIT-04)
- If full-duplex wiring is wrong, half-duplex uses only TX pin (single wire for both directions)
- Eliminates RX pin and crossing as variables
- Fix: Remove `SERIAL_USART_FULL_DUPLEX`, use only TX pin
- Confidence: LOW (workaround, not root cause)
- Maps to: DIAG-02

H5: **SPLIT_USB_DETECT timing** (from AUDIT-05)
- If serial never initializes, the slave cannot detect it lacks USB, creating a deadlock
- Less likely because SPLIT_USB_DETECT uses USB VBUS sensing, not serial
- Fix: Replace with `MASTER_LEFT` for testing
- Confidence: LOW
- Maps to: DIAG-05
